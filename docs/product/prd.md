# 产品需求文档（PRD）

## 1. 背景

当前小区内部租赁信息通常散落在微信群、公告栏或个人私聊中，信息可信度、时效性和管理效率都较差。项目希望通过统一的信息发布和审核平台，降低信息获取成本，提升可信度。

## 2. 目标

首期版本实现一套可用的“发布 - 审核 - 展示”闭环，覆盖房屋和车位两类租赁信息。

## 3. 用户角色

### 住户用户

- 使用微信小程序登录
- 发布房屋或车位出租信息
- 查看自己发布内容的审核状态
- 浏览已通过审核的信息
- 直接联系发布者

### 管理员

- 登录管理后台或后台接口
- 查看待审核内容
- 审核通过或拒绝
- 对异常内容执行强制下架

## 4. 核心业务流程

### 4.1 住户发布租赁信息

1. 用户登录小程序
2. 选择发布类型：房屋 / 车位
3. 填写标题、描述、价格、联系方式等字段
4. 上传图片
5. 提交后状态为 `PENDING`

验收标准：

- 必填字段校验明确
- 提交成功后能看到待审核状态
- 未审核内容不得对其他用户公开

### 4.2 管理员审核

1. 管理员查看待审核列表
2. 进入详情页核对信息
3. 选择通过或拒绝
4. 拒绝时必须填写原因

验收标准：

- 待审核列表按提交时间倒序
- 拒绝原因可被发布者查看
- 审核操作保留操作者和时间

### 4.3 信息展示

1. 普通用户浏览已审核通过的房屋或车位信息
2. 用户按类型或状态筛选
3. 用户查看详情并联系发布者

验收标准：

- 仅 `APPROVED` 状态可公开展示
- 详情页可直接触达联系方式
- 已下架或被拒绝信息不在公开列表展示

## 5. 功能清单

### 必做

- 用户体系基础能力
- 微信登录或模拟登录能力
- 租赁信息 CRUD 基础能力
- 审核状态流转
- 管理员登录和审核接口
- 基础日志和异常处理

### 可后置

- 消息通知
- 多图片排序
- 搜索和高级筛选
- 数据统计看板

## 6. 非功能需求

- 接口统一返回结构
- 所有时间字段统一时区和格式
- 核心流程可审计
- 首期优先可维护性，不做过度复杂架构

## 7. 数据与状态要求

### 租赁类型

- `HOUSE`
- `PARKING`

### 审核状态

- `PENDING`
- `APPROVED`
- `REJECTED`
- `OFFLINE`

## 8. 非目标范围

- 不做社交广场
- 不做推荐流
- 不做租约签署
- 不做支付担保

## 9. 待确认事项

- 微信真实登录接入的时间点
- 是否需要独立管理后台前端
- 图片文件存储方案
- 管理员权限是否区分角色等级
